## 1. Android TV и заикание звука

### 1.1 Что показывают журналы

**Throttle в AudioFlinger.** В сессии 04.08 (3 ч 05 мин) — 1523 строки
`AudioFlinger: mixer(...) throttle end: throttle time(N)`, в сессии 24.04 — 388 за 2 ч.
Эта строка пишется миксером Android, когда запись в аудио-HAL вернулась
**быстрее половины буфера**: эмулированное устройство то не принимает данные,
то принимает пачкой. То есть подача звука из гостя на хост идёт рывками.

Распределение интервалов между событиями — без периода (0–40 с, плавно
спадает), равномерно по всему сеансу. Значит, это не один «виновник» с таймером
(health check раз в 30 мин, позиционирование раз в 500 мс и т.п.), а
**постоянный джиттер планирования хоста**, на который накладывается слишком
маленький запас в аудиобуфере.

Других признаков проблемы в госте нет: нехватки памяти нет (MemAvailable ~2.7 ГБ),
`lowmemorykiller` не срабатывал, `Choreographer: Skipped frames` — 7 раз за 3 часа.

**Приоритеты.** Во всех журналах:
```
Emulator process priority set to ABOVE_NORMAL     ← PID лаунчера emulator.exe
WinEvent: re-exec PID 2880 → 7632                 ← реальный qemu — другой процесс
Thread boost complete: 67 × ABOVE_NORMAL, 0 × TIME_CRITICAL (audio)
NOTE: audio thread not identified by name
```
В сессии 04.05 буст сработал раньше, чем нашёлся qemu: `6 × ABOVE_NORMAL` — то
есть повышены потоки лаунчера, который ничего не делает.

### 1.2 Причины (по убыванию вероятности) и что делать

#### A. Неверные параметры аудио QEMU — `AndroidTVLifecycle.cpp:942–956`, `ProfileDetails.qml:184–249` — ✅ сделано

1. **`QEMU_AUDIO_TIMER_PERIOD` — частота в Гц.** Это подтверждено в коммите QEMU
   *«audio: fix audio timer rate conversion bug»*: переменная окружения осталась
   частотой. Эмулятор Android собран на QEMU 2.12, где действуют именно эти
   переменные; по умолчанию 100 Гц (= 10 мс).
   В UI переключатель включает «100 мс» (случайно совпадает с умолчанием),
   кнопки шагают ±10 в диапазоне 10–500. Пользователь, уменьшая «мс» ради
   «меньшей задержки», получает **10 Гц = период 100 мс** → звук рвётся
   гарантированно. Увеличивая «для стабильности» до 500 — получает период 2 мс и
   лишнюю нагрузку.
   → Переименовать в «Частота аудиотаймера, Гц» или пересчитывать
   `Hz = 1000 / ms` в C++. Разумный диапазон 100–250 Гц.

2. **`QEMU_DSOUND_LATENCY_MILLIS` без `QEMU_DSOUND_BUFSIZE_OUT`.** В dsound-бэкенде
   QEMU 2.x latency — это начальный отступ записи внутри кольцевого буфера
   DirectSound, а сам буфер по умолчанию 16384 байта (~93 мс при 44.1 кГц стерео).
   Отступ считается как `(latency − текущая_дистанция) % bufsize`. UI по
   умолчанию ставит **200 мс** → после остатка от деления запас ~14 мс; 100 мс →
   ~7 мс. Т.е. ручная настройка, задуманная как «больше запас», делает его
   меньше и непредсказуемым.
   → Всегда выставлять пару: `QEMU_DSOUND_BUFSIZE_OUT=65536` (~370 мс) и
   `QEMU_DSOUND_LATENCY_MILLIS` 40–80 мс; в UI ограничить latency ≤ 0.6·буфера.
   Начальное значение для теста: **буфер 65536, latency 60** (это +60 мс задержки
   звука — для ТВ незаметно, а запас от джиттера вырастает в 6 раз против
   умолчания 10 мс).

3. Режим «auto» = умолчания QEMU (10 мс запаса). Для машины, которая
   одновременно рисует 1440p-интерфейс, держит LL-хуки и опрашивает DS4Windows,
   10 мс мало. Я бы сделал безопасные значения из п.2 умолчанием.

#### B. Эмулятор — фоновый процесс (архитектура «прозрачного окна сверху») — 🟡 минимальные шаги сделаны, схема — нет

`AndroidTVWindow.cpp:451–468`: эмулятор показывается **под** окном MediaStation,
MediaStation становится alpha = 0, остаётся TOPMOST и забирает фокус
(`SetForegroundWindow(m_mediaStationHwnd)`). Плюс `main.cpp:154–155` делает окно
MediaStation `WS_EX_LAYERED` **навсегда**, с самого старта.

Последствия:
- Процесс эмулятора не foreground: в клиентских Windows foreground-процесс
  получает увеличенный квант; фоновые процессы могут попадать под
  Power Throttling / EcoQoS, на процессорах Intel 12+ поколения — на E-ядра.
  Для эмулятора, где vCPU и аудиотаймер должны просыпаться каждые 10 мс, это
  именно «периодические» провалы.
- `timeBeginPeriod(1)` (`AndroidTVLifecycle.cpp:961`) вызывается в процессе
  **MediaStation**. С Windows 10 2004 разрешение таймера действует только на
  вызвавший процесс — эмулятору это не помогает. С Windows 11 запрос высокого
  разрешения от процесса, чьи окна полностью перекрыты/невидимы, система вправе
  игнорировать.
- Полноэкранное layered-окно поверх 1440p-видео — лишняя композиция DWM на
  каждый кадр, и эмулятор теряет возможность прямого вывода (independent flip).
  Насколько это бьёт по производительности на конкретной видеокарте — надо
  мерить, но выигрыша от такой схемы нет никакого.
- Постоянный `WS_EX_LAYERED` у основного окна Qt Quick (D3D11) — рискованное
  сочетание само по себе; держать его включённым, когда ТВ не запущен, незачем.

**Это решение я считаю ошибочным.** Оно появилось, чтобы ловить кнопку «Меню»
и показывать оверлей. Но хук клавиатуры (`G72KeysModule`) уже глобальный, а
оверлей — отдельное Tool-окно (`OverlayModule`), которому не нужно прозрачное
полноэкранное окно под собой.

→ Предлагаемая схема:
1. При показе ТВ: эмулятор — обычное окно без рамки на весь экран,
   **на переднем плане и с фокусом**; MediaStation — `SW_HIDE` (или свернуть);
   `WS_EX_LAYERED` вообще не нужен.
2. «Меню» ловится существующим LL-хуком → показывается окно оверлея (TOPMOST,
   небольшое). При закрытии — фокус обратно эмулятору.
3. Выход из ТВ: показать MediaStation, скрыть эмулятор.
4. Кнопки пульта при этом можно отдавать эмулятору **как обычные нажатия
   клавиатуры** (у эмулятора `hw.keyboard=yes`, `hw.dPad=yes`) — см. п. D.

Если переделка сейчас не по силам — минимальные шаги внутри текущей схемы:
- Найти **qemu-процесс** (он уже определяется в WinEvent-хуке) и уже ему
  поставить `ABOVE_NORMAL_PRIORITY_CLASS` (лучше `HIGH`), а не лаунчеру.
- Отключить троттлинг питания для qemu-процесса:
  `SetProcessInformation(h, ProcessPowerThrottling, …)` с
  `ControlMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED |
  PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`, `StateMask = 0`.
- Убрать «буст потоков через 3 с» (`AndroidTVLifecycle.cpp:1057–1116`): поиск
  аудио-потока по имени не сработал ни разу, а одинаковое ABOVE_NORMAL на все
  ~67 потоков qemu ничего не даёт сверх класса процесса. `TIME_CRITICAL` на
  чужие потоки, если когда-нибудь сработает, — способ подвесить систему.
- `WS_EX_LAYERED` ставить только на время показа ТВ и снимать при выходе.

#### C. Нагрузка на хост во время ТВ — ✅ сделано (кроме `RegisterDeviceNotification` для геймпадов)

#### D. Ввод с пульта — ✅ сделано: консоль эмулятора, запасной путь — `input keyevent`

`AndroidTVInput.cpp:196`: `input keyevent N` — это запуск `app_process` (JVM) в
Android на каждую пачку нажатий: 200–500 мс CPU гостя. Пачкование уже сделано,
но при навигации гость всё равно грузится → заикание во время листания.

→ Варианты дешевле на порядки:
- Отдавать нажатия **окну эмулятора** как клавиатуру (`PostMessage WM_KEYDOWN`
  стрелок/Enter/Esc в окно эмулятора, или `SendInput`, если эмулятор в фокусе —
  см. схему в B). Эмулятор сам переводит их в события D-pad без JVM.
- Или консоль эмулятора (TCP `localhost:<consolePort>`, авторизация токеном из
  `%USERPROFILE%\.emulator_console_auth_token`): `event send EV_KEY:KEY_UP:1` /
  `…:0` — прямой ввод в виртуальное устройство.

#### E. Мелочи в модуле — 🟡 `emu kill` и метрика сделаны, `Android_TV.log` через `LoggerWorker` — нет

- `stop()` → через 6 с `killEmulatorTree()`; `shutdown()` — сразу `TerminateProcess`
  всего дерева без `emu kill`: при выходе из программы во время работы ТВ
  userdata.qcow2 может остаться в «грязном» состоянии. Лучше `emu kill` и ждать
  1–2 с, потом убивать.
- `Android_TV.log` пишется построчно с `flush()` в GUI-потоке и логирует каждое
  нажатие (`[Input] keyevent`). Объёмы небольшие, но писать лучше через
  `LoggerWorker`, как основной журнал.
- Health check раз в 30 мин пишет в основной журнал MemAvailable/SwapFree —
  полезнее писать **счётчик underrun'ов звука**:
  `adb shell dumpsys media.audio_flinger` → строки `Underruns`. Это даст
  объективную метрику заикания вместо субъективной.

## 2. Обновление

### 2.1 Что сейчас

```
Сервер: путь к exe + qml + windeployqt + версия руками → копия во временную папку
        → windeployqt → 7z -mx5 → SHA-256 → TCP на 12345 (push)
Клиент: принимает (без вопроса) → диалог «есть обновление» → копия Updater в %TEMP%
        → Updater ждёт выхода → распаковка → rename папки приложения целиком в
        MediaStation_Old_* → новая папка на место → перенос data/ и tools/ обратно
```

### 2.2 Проблемы

1. ✅ (файл `app_version.txt`, сервер читает версию из exe) **Версия не работает.** `UpdateManager.cpp:22–24` — `#ifndef MEDIASTATION_VERSION
   #define "1.0.0"`, а `Version.h` не подключён. Логгер подключает `Version.h`,
   `UpdateManager` — нет, сравнение всегда с «1.0.0». Версию на сервере вводят
   руками (`UpdateTab.cpp:601`) — ничто не связывает её со сборкой.
2. ❌ **Перенос всей папки приложения** ради замены exe и пары DLL. Отсюда весь
   сложный код отката (rename/пофайловый перенос/повторы/«oldDir сохранён»),
   зависимость от того, держит ли Проводник или антивирус папку.
3. 🟡 (недостающее из старой `tools/` теперь переносится) **«Мажорное» обновление удаляет `tools/`** старой версии целиком
   (`UpdaterWindow.cpp:766–818`), переносится только `android-tv/avd`. Если в
   архиве `tools` неполный (нет модели LLM, ffmpeg, системного образа, DS4Windows,
   Android SDK), они пропадут вместе с `MediaStation_Old_*`. Галочка «Исключить
   tools» на сервере — единственная защита, и по умолчанию она **выключена**.
4. ✅ **`logs/` не переносятся** — после обновления пропадают журналы прошлой
   версии, включая `Android_TV.prev.log`, которые нужны для разбора проблем.
5. ❌ **Каждый раз — полный пакет**: exe + все Qt DLL + QML-плагины + (по умолчанию)
   весь tools. QML при этом и так вшит в ресурсы (`qml.qrc`), копирование папки
   `qml` в пакет нужно только для `windeployqt --qmldir`.
6. ❌ **Нет подлинности.** SHA-256 присылает тот же, кто присылает архив, — это
   проверка целостности, не подписи. Любой компьютер в локальной сети может
   отправить «обновление» (`NetworkServer.cpp:103–131` принимает без вопроса),
   пользователю покажут диалог — одно нажатие «ОК», и чужой exe запущен.
7. ✅ Сервер при сетевой ошибке удаляет подготовленный архив
   (`UpdateTab::abort → cleanup → cleanupArchive`) — повтор = заново windeployqt и 7z.

### 2.3 Предлагаемая схема (простая)

**Источник версии один:** `VERSION` в корне репо → qmake генерирует `Version.h` и
ресурс `VERSIONINFO` в exe. Сервер читает версию **из exe**, поле ввода убрать.

**Пакет = манифест + только файлы приложения:**
```
manifest.json  { version, files: [{path, size, sha256}], signature }
MediaStation.exe, *.dll, platforms/, qml/ (плагины Qt), Updater/…
```
`tools/`, `data/`, `logs/` в пакет **не входят никогда**. Тяжёлые компоненты
(Android SDK, модель LLM, ffmpeg, DS4Windows) — отдельные «компоненты» со своей
версией и отдельной кнопкой, они меняются раз в полгода.

**Доставка — pull, а не push.** Сервер публикует последнюю версию (HTTP на
сервере в локалке или просто GitHub Releases). Клиент при старте и по кнопке
«Проверить обновления» скачивает манифест, сравнивает хэши с установленными
файлами и докачивает **только изменившиеся** (обычно exe + 1–3 DLL, десятки МБ
вместо сотен).

**Замена — пофайловая, без переноса папки:** Updater для каждого файла:
`file → file.old`, `new → file`; список `.old` — это готовый откат. Новая версия
через 30–60 с работы пишет «healthy»; если её нет — при следующем старте
Updater возвращает `.old`. Код Updater сокращается в разы.

**Подпись:** ECDSA P-256 через Windows CNG (`BCryptVerifySignature`) — без новых
библиотек. Закрытый ключ на сервере, открытый вшит в клиент. Подписывается
манифест.

**Сервер — одна кнопка** «Собрать и опубликовать» (и тот же режим из командной
строки для Qt Creator/CI): найти exe → `windeployqt` → манифест → подпись →
опубликовать. Медиацентр получает уведомление «доступна версия X» сам.

Если pull делать не хочется: можно оставить push, но с манифестом/дифом и
сопряжением (п. 3.3).

## 7. Что считаю плохими решениями (прямо)

1. **Прозрачное TOPMOST-окно MediaStation поверх эмулятора.** Сложно (таймеры
   «держи TOPMOST», синхронизация позиции, cooldown'ы оверлея, `SetForegroundWindow`),
   ломает игры (уже чинили «чёрный экран под TOPMOST»), лишает эмулятор статуса
   переднего плана и почти наверняка участвует в заикании. Эмулятор должен быть
   обычным окном на переднем плане, оверлей — маленьким окном поверх.
2. **Повышение приоритета «вслепую»** (буст всех потоков через 3 с, поиск
   «audio» в именах потоков, `TIME_CRITICAL`). Не работает (по журналам), а если
   заработает — может подвесить систему. Нужен класс приоритета qemu-процесса и
   отказ от троттлинга — всё.
3. **Ручные «мс» для параметров QEMU**, которые на деле Гц и смещение в
   кольцевом буфере. Это и есть, скорее всего, большая часть «уже очень много
   предпринято, а звук заикается»: часть «исправлений» делала хуже.
4. **Обновление переносом всей папки + перенос `tools` обратно.** Сложно,
   хрупко и опасно для гигабайтных данных. Пофайловая замена по манифесту проще
   и безопаснее.
5. **Push-доставка без сопряжения** — любой в сети может прислать exe.
6. **Опрос DS4Windows запуском процессов каждые 5 с** и **запуск игр через
   PowerShell** — дорого там, где можно обойтись системным API.

### 9.3 Нейросети в целом

Сейчас три независимых «владельца» видеопамяти: `GameInfoModule` (Qwen-7B),
`SongNameResolver` (тот же Qwen-7B, **второй экземпляр**), Whisper (до 3 ГБ),
плюс Demucs (CPU). Каждый грузит и выгружает модель сам, общей очереди нет,
путь к модели захардкожен в двух местах (`GameInfoModule.cpp:289`,
`SongNameResolver.cpp:35`), а настройка `llamaModelPath` читается из ключа
реестра, в который никто не пишет (§4 п.3).

→ Один сервис `LocalAI` (модуль): реестр моделей в `tools/models/models.json`
(путь, размер, назначение), очередь задач с приоритетом, правило «одна большая
модель в видеопамяти», статус для UI («Нейросеть занята: описание игры, 40 %»),
и **не запускать тяжёлые модели, пока работает игра или Android TV** (иначе
отнимают видеопамять и CPU, что напрямую бьёт по звуку из §1).

Описание игры без интернета: `GameInfoModule` пишет в журнал «LLM will use its
own knowledge», в промпте просит «если не уверен — пустая строка», но текст
показывается как обычно. 7B-модель по памяти всё равно часто выдумывает
разработчиков, даты и жанры. Офлайн-описание надо явно помечать «без
источников, может быть неточно» или не генерировать по умолчанию.

### 10.2 Образ Android TV — держать локально, но не в git

Согласен: образ должен лежать локально. Но место ему **не в git**:
`system.img` 1–4 ГБ, GitHub не принимает файлы больше 100 МБ, LFS — с квотой,
а история репозитория разрастётся навсегда.

Вместе с образом есть и другие тяжёлые «компоненты», без которых офлайн
ничего не работает: Android SDK (emulator + platform-tools + образ), JDK,
модель LLM (~4.7 ГБ), модели Whisper (1.6–3 ГБ), `htdemucs.onnx`, ffmpeg,
7zr, DS4Windows, dnsproxy, `applications.json`.

**Предложение — «склад компонентов»:**

```
MediaStation_Components/
  components.json        ← имя, версия, размер, sha256, куда ставить
  android-sdk-34-tv.7z   ← emulator + platform-tools + system-images;android-34;android-tv;x86
  jdk-17.7z
  llm-qwen2.5-7b-q4.7z
  whisper-large-v3-turbo.7z
  demucs-htdemucs.7z
  ffmpeg.7z  7zr.exe  ds4windows.7z  dnsproxy.7z  steam-applist.7z
```

- Хранится на сервере (MediaStationServer уже есть в каждой установке «ТВ +
  рабочий компьютер»), на флешке или NAS. Первичная установка и
  восстановление — только из него, без интернета.
- Вкладка «Компоненты» на сервере: что установлено на медиацентре, какие
  версии, кнопка «Доставить/обновить компонент» (тот же протокол, что для
  обновлений, но с `kind: "component"`).
- `setup_android_sdk.bat` переделать: распаковать `android-sdk-34-tv.7z`
  и создать AVD. Скачивание через `sdkmanager` — только как вариант
  «собрать компонент заново» на машине разработчика.
- Updater **никогда не трогает компоненты**: обновляется только приложение
  (§2.3). Сейчас «мажорное» обновление удаляет старую `tools/` — то есть может
  стереть образ, который потом без интернета не восстановить.
- `external_tools/cmdline-tools` в git тогда не нужен (он только загрузчик
  для онлайн-сборки компонента).

## 11. Чего нет совсем (не по бэклогу, по коду)

1. **Навигация фокусом с пульта/геймпада.** Во всём QML нет `KeyNavigation` и
   управления фокусом (кроме одного поля в караоке). Обработчики
   `onLeftPressed`, `onRightPressed`, `onSelectPressed` в `Main.qml` — пустые;
   стрелки вверх/вниз только прокручивают экран. Интерфейс работает **только
   как «аэромышь»**. Для медиацентра на ТВ это главная недоделка: геймпад
   DualShock и обычный пульт без гироскопа не могут управлять меню.
   Нужен общий механизм фокуса (подсветка выбранной плитки, переход стрелками,
   OK = клик, Назад = закрыть диалог) — на нём же решается пункт бэклога
   «стрелки в диалогах».
2. **Сообщение о неудачном запуске игры.** `GameWatcher` шлёт `launchFailed`,
   C++ публикует `game/failed`, а QML только пишет `console.warn`
   (`Main.qml:392`). Пользователь видит, что «ничего не произошло».
3. **Отслеживание запуска для обычных `.exe` и ярлыков.** Через `launch.ps1`
   запускаются только установленные игры; всё остальное — `QDesktopServices::openUrl`
   (`AppController.cpp:172`) без затемнения, без определения закрытия и без
   паузы опроса геймпадов.
4. **Оверлей в игре** — модуль есть, но нигде не вызывается (отмечено ещё в
   прошлых правках).
5. **Выключение компьютера** — кнопка «Выключить» вызывает `Qt.quit()`
   (`PowerMenu.qml:176`), т.е. просто закрывает программу.
6. **Сборка релиза**: нет настроек оптимизации (LTCG), нет компиляции QML
   (`qtquickcompiler`), нет установщика.
7. **Архивация игр** (`tools/SevenZip.cpp:152–153`): `-m0=lzma2 -mx=9` для
   игр в десятки ГБ — часы работы и ~0.7 ГБ ОЗУ на поток, а файлы игр в
   основном уже сжаты и почти не ужимаются. Для «хранилища» разумнее `-mx=1`
   (или `-mx=3`) с `-mmt`: в разы быстрее при небольшой разнице в размере.

## 14. Караоке — почему работает плохо

Расставил по тому, насколько каждая причина портит результат.

### 14.1 Текст не совпадает с музыкой (самое заметное)

1. ✅ **Берётся не та версия текста с lrclib.** Длительность трека всегда 0
   (TagLib не подключён, §9.2 п.2), поэтому из результатов поиска берётся
   **первый** синхронизированный (`LrcFetcher.cpp:124–137`). Если это радио-версия,
   а у вас альбомная (другое вступление), все строки сдвинуты на секунды, и
   никто это не проверяет.
   → Длительность известна бесплатно: после первого шага есть WAV 44.1 кГц,
   `длительность = размер_данных / 176400`. Передавать её в поиск и брать вариант
   с разницей ≤ 3 с; если таких нет — считать, что синхронного текста нет.
   → Проверка сдвига без Whisper: дорожка вокала уже выделена, VAD
   (`VoiceActivity`) уже есть. Сравнить начала строк LRC с началами участков
   голоса, найти общий сдвиг (перебор −10…+10 с с шагом 50 мс) и применить.
   Если совпадение плохое — уйти в Whisper.

2. ✅ **Время слов от Whisper неточное.** Используются обычные `token_timestamps`
   (`WhisperWrapper.cpp:193`). В whisper.cpp они грубые (часто «съезжают» на
   сотни мс, особенно в пении). Для караоке есть режим **DTW**:
   `cparams.dtw_token_timestamps = true`, `cparams.dtw_aheads_preset =
   WHISPER_AHEADS_LARGE_V3_TURBO` (или `…_LARGE_V3`), а время брать из
   `whisper_token_data.t_dtw`. Это ровно для пословной синхронизации.

3. ✅ **Дорожки вокала и минуса расходятся** — два отдельных `MediaPlayer`
   (§9.2 п.6). При включённом вокале — эхо; подсветка идёт по позиции вокала,
   а слышно в основном минус.

### 14.2 Текст неправильный

4. ✅ **Фильтр «галлюцинаций» выкидывает настоящие слова.** Список
   (`WhisperWrapper.cpp:216–220`) сравнивается через `contains`: из песни
   пропадут «перевод», «редактор», «создавал», фамилии «Егоров», «Сёмкин»,
   любое слово с «субтитр». Фильтровать надо **целые фразы** в конце/начале
   трека, а не подстроки в любом месте.
5. ✅ **Язык фиксируется по одному участку.** Самый длинный участок мог оказаться
   с английским припевом — тогда вся русская песня распознаётся как английская.
   Лучше определить язык по 2–3 участкам (большинством) или дать выбор в UI.
6. ❌ **Нет GigaAM** для русского языка (§9.2 п.11).

## 23. Блокировка рекламы в Android TV — AdGuard Home вместо dnsproxy

Решение от 05.11: блокировщик — **AdGuard Home**, обход блокировок — **zapret**
(§24). dnsproxy убираем: AdGuard Home делает всё то же самое и плюс фильтры.

**Про «не продаётся».** AdGuard Home — открытый проект (лицензия GPLv3),
бесплатный, без платных тарифов; ставится и работает у вас на компьютере.
Списков «разрешённой рекламы» за деньги, как у Adblock Plus (программа
Acceptable Ads), у него нет — блокируется то, что есть в выбранных вами
списках фильтров. По умолчанию подключён «AdGuard DNS filter»; можно
добавить свои списки, в том числе **файлом с диска** — для работы без
интернета. Скачанные списки хранятся локально и работают офлайн, обновляются,
когда интернет есть.

**Почему сейчас ничего не блокируется** (то же, что было с dnsproxy):
эмулятору передаётся `-dns-server 8.8.8.8,1.1.1.1`
(`AndroidTVLifecycle.cpp:979–986`), порт у этой опции всегда 53, поэтому
прокси на 5300 не используется; блоклист пишется только в системный hosts,
а это работает лишь на образах с root.

**Как встроить:**
1. AdGuard Home — компонент на складе (§10.2): `tools/adguardhome/AdGuardHome.exe`
   + `AdGuardHome.yaml` с готовыми настройками. Ставится **службой Windows один
   раз** при установке (`AdGuardHome.exe -s install`, нужны права
   администратора) — дальше MediaStation админ не нужен.
2. В `AdGuardHome.yaml`: DNS слушает только `127.0.0.1:53` (не всю сеть),
   веб-интерфейс — только `127.0.0.1`, upstream — DoH (зашифрованный DNS: его же
   рекомендует zapret для YouTube), включены локальные списки фильтров.
3. MediaStation перед запуском эмулятора проверяет, что `127.0.0.1:53` отвечает
   (один DNS-запрос), и тогда запускает эмулятор с `-dns-server 127.0.0.1`.
   Не отвечает — DNS из профиля, как сейчас, плюс строка в журнал.
   **Проверить на Windows**, что эмулятор принимает адрес `127.0.0.1`
   (документация Google об этом не пишет): `adb shell nslookup doubleclick.net`.
4. Удалить: `startDnsProxy/stopDnsProxy`, `applyBlocklist` (`adb root`, запись в
   `/system/etc/hosts`), `adb reverse`, создание `dnsproxy.yml` и `default.txt`
   в `setup_android_sdk.bat`.
5. В настройках Android TV: «Блокировка рекламы: вкл/выкл», статус службы,
   кнопка «Открыть панель AdGuard» (веб-интерфейс на `127.0.0.1`).
6. Не направлять весь Windows на `127.0.0.1` — только эмулятор. Иначе если
   служба остановится, без DNS останется весь компьютер.

**Ограничения:**
- Рекламу **внутри YouTube** DNS-блокировка не убирает (реклама с тех же
  серверов, что видео). Наоборот: агрессивные списки иногда ломают YouTube —
  zapret прямо советует при проблемах с YouTube отключить блокировщик. Нужен
  белый список доменов YouTube/Google Video в AdGuard Home.
- Приложения со своим зашифрованным DNS идут мимо.
- Порт 53 на `127.0.0.1` обычно свободен; если занят чем-то ещё — использовать
  `127.0.0.2`.

## 24. zapret (flowseal/zapret-discord-youtube) — как встроить

**Что это.** Сборка zapret под Windows (лицензия MIT): программа `winws.exe` и
драйвер WinDivert из проекта bol-van/zapret, плюс готовые наборы настроек
(«стратегии» `general*.bat`) и `service.bat` для установки службой.
WinDivert перехватывает исходящий трафик **всей системы** и для доменов из
списка подмешивает «обманные» пакеты, чтобы оборудование провайдера (DPI) не
узнало соединение.

**Главное для MediaStation: Android TV получает обход автоматически.**
Эмулятор выходит в интернет через обычные сокеты процесса qemu на этом же
компьютере, поэтому winws видит и его трафик (имя сайта в TLS у YouTube-клиента
в Android то же самое). Ничего настраивать внутри Android не нужно.

**Как встроить:**
1. Компонент на складе (§10.2): `tools/zapret/` — распакованный релиз
   (без кириллицы и спецсимволов в пути — требование сборки).
2. Установка **службой один раз** через `service.bat` → Install Service, с
   выбранной стратегией (права администратора). MediaStation сам `winws` не
   запускает: каждый запуск требовал бы права администратора.
3. MediaStation только **показывает статус** (служба есть/запущена — это можно
   узнать без прав админа) и при желании кнопку «Проверить» (открывается ли
   YouTube). Подбор стратегии — вручную, через их `service.bat`: какая
   стратегия работает, зависит от провайдера, и со временем она перестаёт
   работать — это нормально для zapret, в README так и написано.
4. **Game Filter не включать.** Он расширяет обход на все порты выше 1023 —
   это игры. На игровом компьютере это лишний риск задержек.
5. Связка с §23: zapret для YouTube советует «Secure DNS» — его и даёт AdGuard
   Home с DoH-upstream. Домены YouTube добавить в белый список AdGuard Home.

**Риски, о которых надо помнить:**
- **Антивирусы** ругаются на WinDivert (`RiskTool.Multi.WinDivert`) — папку
  нужно добавить в исключения.
- **Античиты** в некоторых онлайн-играх реагируют на загруженный драйвер
  WinDivert. В zapret-win-bundle есть инструкция `windivert-hide`. Для
  медиацентра с играми это стоит проверить на ваших играх.
- Проверка обновлений zapret идёт через интернет; офлайн служба просто
  работает с той версией, что стоит.

### 24.1 Автоматизация zapret — что можно и как

Проверил содержимое релиза (`service.bat` v1.10.4, `utils/test zapret.ps1`,
`utils/targets.txt`). В сборке уже есть почти всё нужное, но в виде
интерактивных меню для человека. Это можно делать автоматически.

**Что уже есть в zapret и как это работает:**
- **Стратегии** — 23 файла `general*.bat`; в каждом одна команда `winws.exe` с
  параметрами. `service.bat` вытаскивает эти параметры и создаёт службу
  `zapret` (`sc create … start= auto`), имя выбранной стратегии пишет в реестр
  (`HKLM\System\CurrentControlSet\Services\zapret`, значение
  `zapret-discord-youtube`).
- **Автотест стратегий** (`test zapret.ps1`): по очереди запускает каждую
  стратегию, ждёт `winws.exe`, проверяет `curl` сайты из `targets.txt`
  (YouTube, `redirector.googlevideo.com`, `i.ytimg.com`, Discord, Google,
  Cloudflare) по HTTP/TLS 1.2/TLS 1.3 + ping, пишет результаты в
  `utils/test results`. Есть отдельный режим «DPI checkers».
- **Проверка обновлений**: читает версию с
  `raw.githubusercontent.com/Flowseal/zapret-discord-youtube/main/.service/version.txt`
  и **только открывает страницу релиза** — сам не скачивает.

**Как автоматизировать в MediaStation:**

1. **Одна служба-помощник с правами** («MediaStation Helper», ставится
   установщиком один раз, дальше никаких запросов администратора). Она умеет
   то, что требует прав: ставить/менять/останавливать службу zapret и службу
   AdGuard Home (§23), добавлять правила брандмауэра (бэклог, блок 6),
   выключать компьютер (§11 п.5). MediaStation общается с ней по именованному
   каналу. Без такого помощника каждый подбор стратегии = окно UAC на ТВ.
2. **Автоподбор стратегии** — повторить логику `test zapret.ps1` в помощнике:
   по очереди запустить `winws` с параметрами каждой стратегии (разбор
   `general*.bat` — как в `service.bat`), проверить цели, выбрать лучшую,
   установить службой. Займёт несколько минут; запускать, когда ТВ не
   используется (или по кнопке «Подобрать заново»), с прогрессом на экране.
3. **Важная доработка теста**: их проверка — `curl -I` (только «открывается или
   нет»). Для YouTube в России проблема обычно в **скорости** видео, а не в
   открытии. Нужен замер скорости: скачать несколько мегабайт реального
   видеопотока (`googlevideo.com`). Ссылку на поток получить для
   тестового ролика можно, например, через `yt-dlp` (тоже компонент на складе).
   Без этого автоподбор может выбрать стратегию, при которой YouTube
   «открывается, но не грузит видео».
4. **Самоконтроль**: раз в N часов и при старте Android TV — короткая
   проверка текущей стратегии (тот же замер, секунды). Стала плохой — тихо
   запустить подбор заново и показать уведомление.
5. **Запоминать стратегию для сети**: провайдер определяется по сети
   (шлюз/MAC роутера или публичный адрес). Переехали/сменили провайдера —
   подбор только при первом подключении, дальше из памяти.
6. **Обновления**: помощник раз в сутки читает тот же `version.txt`; новая
   версия скачивается **на сервер-склад** (§10.2) или во временную папку,
   проверяется (SHA-256, как советует автор сборки — сверка с исходниками
   bol-van), затем: остановить службу → заменить `bin/` и `lists/`, **сохранив
   `*-user.txt`** → прогнать проверку → если стало хуже, вернуть старую версию.
   Без интернета — ничего не делает, работает текущая.
7. **Списки** (`ipset-all.txt`, хост-листы) обновлять так же; свои домены —
   в `list-general-user.txt` (zapret их не перезаписывает).

**Ограничения:**
- Обновлять автоматически программу, которая загружает драйвер ядра, —
  риск: подменённый релиз = полный доступ к компьютеру. Поэтому проверка
  хэшей обязательна, а включение автообновления — настройкой (по умолчанию —
  «скачать и спросить»).
- Диагностика сборки сама находит конфликтующие программы (Killer, Intel
  Connectivity Network Service, Check Point, SmartByte, VPN) — эти проверки
  стоит перенести в помощник и показывать в настройках.
- Подбор не гарантирует результат: если провайдер блокирует жёстче, ни одна
  стратегия не подойдёт — тогда сообщение «обход не найден», а не бесконечный
  перебор.
